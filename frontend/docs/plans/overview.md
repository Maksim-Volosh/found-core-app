# Фронтенд: этапы F0–F9. Документ для исполнителя

Папка: `frontend/`. Ветка каждого этапа: `feat/frontend-<имя>`. Перед началом прочитать `CLAUDE.md` в корне, `frontend/CLAUDE.md` и `frontend/docs/rules.md`: они обязательны. Этот документ ничего не отменяет, он раскладывает работу на этапы. Подробный план каждого этапа пишется отдельным файлом перед его началом, как для бэкенда (первый уже есть: `f0-skeleton.md`).

## 0. Как работать с этим документом

1. **Любое ключевое решение можно пересмотреть, но только осознанно.** Если выбираешь другой вариант или нашёл проблему, которой здесь нет, допиши в раздел 9 «Отклонения»: что изменил, почему, что отброшено.
2. Один этап: одна ветка и один PR. Между этапами `main` не ломается: каждый этап заканчивается зелёными проверками (раздел 7).
3. Если пункт плана оказался неверным, исправь план в том же коммите, а не только код.
4. Проверки (`npm ci`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`) запускает человек и прикладывает результат. «Работает» без прогона не считается.
5. Этап F1 (дизайн экранов) согласуется до написания кода экранов.

## 1. Контекст и цель

Бэкенд на `main` готов до этапа 7 включительно: вход, справочники, анкеты, эмбеддинги, лента, контакты с уведомлениями. Фронтенда нет, в `CLAUDE.md` стояло «backend only». Цель: Telegram Mini App, который проводит человека от первого входа до открытого контакта и использует каждый готовый эндпоинт.

Что нужно:
- приложение, которое выглядит и ведёт себя как часть Telegram (тема, кнопка «Назад», безопасные зоны);
- все справочные данные и лимиты из API, без копий во фронтенде;
- работа без бэкенда и вне Telegram на моках, чтобы этапы F0 и F1 не ждали чужих задач;
- проверка контракта: схема типов из OpenAPI, формы ошибок покрыты тестами.

## 2. Ключевые решения и почему

План в целом согласован с Максом Волошем 2026-11-06 (сообщение с планом в Telegram). Он видел и принял: решения 1–3, 7–9, 11–14 и 16 (структуру и документы, стек, тему, этапы). Решение 4 (отдельный CI-джоб) в сообщении было вопросом, подтвердить в первом PR. Решения 5, 6, 10 (history-режим роутера), 15, 17–20 и 21 (подписанные коммиты) это уточнения исполнителя, в сообщении их не было: указать их в описании PR и принять или поправить по ревью.

## 3. Технические детали без продуктового эффекта

Предложены исполнителем, отдельно не обсуждались; менять можно с записью в раздел 9.

1. **Структура `src/`.** `app/` (запуск, провайдеры, роутер, ворота), `shared/{api,telegram,ui,i18n,config}`, `features/{auth,onboarding,profile-form,my-profiles,feed,search,contact}`. Зависимости только вниз.
2. **Именование.** Компоненты `PascalCase.tsx` с `PascalCase.module.css`, хуки `useX`, остальное `camelCase.ts`. Только именованные экспорты.
3. **Пагинация ленты.** `useInfiniteQuery`, курсор непрозрачный (не разбирается), размер страницы 20 как по умолчанию у бэкенда.
4. **Подсказки тегов.** Задержка ввода в `shared/config`, один запрос на паузу; бэкенд пока без лимитов на запросы.
5. **Шрифт.** Системный стек по умолчанию (нативный вид, нулевая загрузка). Нужен ли фирменный шрифт, решается в F1.
6. **Ворота входа.** Порядок проверок зафиксирован в `frontend/CLAUDE.md`, раздел «Entry gates».
7. **Типы.** `schema.d.ts` коммитится, обновляется командой `npm run api:types` в том же PR, что и фича, которой нужна новая схема.
