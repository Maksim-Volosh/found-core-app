# Этап F0: skeleton. Документ для исполнителя

Ветка: `feat/frontend-skeleton`. Перед началом прочитать `CLAUDE.md` в корне, `frontend/CLAUDE.md`, `frontend/docs/rules.md` и `frontend/docs/plans/overview.md`: они обязательны. Этот документ ничего не отменяет, он уточняет этап F0.

## 0. Как работать с этим документом

1. **Любое ключевое решение можно пересмотреть, но только осознанно.** Если выбираешь другой вариант или нашёл проблему, которой здесь нет, допиши в раздел 9 «Отклонения»: что изменил, почему, что отброшено.
2. Этап делается **четырьмя частями** (раздел 6) без PR между ними. Часть 0 это документы: её ветка пушится и показывается владельцу бэкенда до того, как появится код. PR один, в конце. Каждая часть заканчивается зелёными проверками (раздел 7), `main` не ломается.
3. Если пункт плана оказался неверным, исправь план в том же коммите, а не только код.
4. Проверки запускает человек и прикладывает результат. «Работает» без прогона не считается.
5. Версии пакетов в реестре меняются: перед установкой сверить ограничения из `frontend/CLAUDE.md` (таблица «Stack») с предупреждениями npm. Не обновлять TypeScript выше 5.9.x и ESLint выше 9.x.

## 1. Контекст и цель

Фронтенда нет. Нужен каркас, на который садятся все следующие этапы: сборка, проверки, граница с Telegram, граница с API, вход и сессия, оболочка приложения. Без экранов анкеты и ленты.

Итог этапа: приложение открывается внутри Telegram (и в браузере на моках), выполняет вход через `POST /auth/telegram`, показывает имя пользователя, умеет показать экран бана и экран ошибки с повтором, использует тему Telegram, а CI проверяет типы, линтер, тесты и сборку.

Сейчас в репозитории есть только бэкенд. Ни одного клиента Telegram SDK и ни одного вызова API со стороны браузера нет.

## 2. Ключевые решения и почему

Общие решения (стек, ветки, правила) в `overview.md`, раздел 2. Здесь только то, что относится к F0. Решения этого списка предложены исполнителем и в сообщении владельцу бэкенда не обсуждались; указать их в описании PR.

### Граница с API

| # | Решение | Почему | Что отброшено |
|---|---|---|---|
| 1 | **Единый тип `ApiError`** с полями `kind` (`network`, `http`, `coded`, `validation`, `invalid_response`), `status` (или `null` для сети), `code` (или `null`), `message` и `detail` (как пришло). Разбор четырёх форм `detail`: строка, объект `{code, message, ...}`, объект `{message, profile}`, список (422). Всё остальное (не JSON, `null`, число, пустой ответ) даёт `invalid_response`, а не исключение. | Экраны переключаются по `code` и `status`, а не по тексту. Бэкенд отдаёт `detail` в разных формах, схема OpenAPI их не описывает. | Бросать сырой `Response`. Разбирать `detail` в каждом экране. |
| 2 | **Типы из `/openapi.json`**, файл `src/shared/api/schema.d.ts` коммитится, обновляется `npm run api:types`. | Контракт не расходится с бэкендом, изменение схемы ломает сборку. | Типы руками. Генерация всего клиента. |
| 3 | **Клиент `openapi-fetch` с одним промежуточным слоем.** Слой добавляет `Authorization: Bearer`, при `401` вызывает вход заново, при `403` со строковым `detail` сообщает о бане. Зависимости (как получить токен, как войти заново, что сделать при бане) **внедряются** через `configureAuth(...)` из `app/`. | Правило из `rules.md`: `shared` не импортирует `features` и `app`. Токен и вход принадлежат функции auth, а клиент лежит в `shared`. | Импорт сессии из `features/auth` внутри `shared/api`. Глобальный синглтон с прямой ссылкой на хранилище. |
| 4 | **`401`: вход заново один раз, запрос повторяется один раз.** Одновременные запросы ждут один и тот же вход (общий промис). Второй `401` даёт ошибку входа. Сам запрос входа повторов не имеет. | Токен живёт 24 часа без refresh (решение бэкенда). Без общего промиса три параллельных запроса сделали бы три входа с одним `initData`. | Повторять без предела. Выходить на первом `401`. |
| 5 | **`403` со строковым `detail` на любом эндпоинте означает бан**, `detail` это причина. Проверка при входе: `user.is_banned`. | Бэкенд отдаёт `403` с `ban_reason`, если пользователя забанили после выдачи токена. | Считать любой `403` баном. Ловить только при входе. |

### Сессия и вход

| # | Решение | Почему | Что отброшено |
|---|---|---|---|
| 6 | **Токен, пользователь и анкеты лежат в модуле-хранилище в памяти**, чтение через `useSyncExternalStore`. Состояние: `idle`, `signing-in`, `signed-in`, `banned`, `error`. | Токен нельзя в `localStorage` (`rules.md`). Контекст перерисовывал бы всё дерево при смене состояния. | `localStorage`. Контекст React с токеном. |
| 7 | **Сырой `initData` берётся только в `shared/telegram`** (`getRawInitData()`). Вне Telegram он бросает `NotInTelegramError`. В режиме разработки возвращает `VITE_DEV_INIT_DATA`, если задан. | `initDataUnsafe` не используется для решений, на сервер уходит сырая строка. | Читать `window.Telegram` в auth. |
| 8 | **Вход при запуске один раз** (защита от двойного вызова в `StrictMode`). Кнопка «Повторить» на экране ошибки запускает его заново. | В режиме разработки React запускает эффекты дважды. Два входа подряд не нужны. | Вход при каждом монтировании. |

### Telegram и тема

| # | Решение | Почему | Что отброшено |
|---|---|---|---|
| 9 | **Обёртка `shared/telegram`** выставляет наружу: `initTelegram()`, `isInsideTelegram()`, `getRawInitData()`, `backButton` (показать, скрыть, подписаться), `openChat(username)`, `haptic`. Каждый метод проверяет версию API и ничего не делает, если метода нет. | Единственное место, где живёт SDK (`rules.md`), одинаково работает в тестах и вне Telegram. | Вызывать SDK из компонентов. |
| 10 | **Тема: `themeParams.bindCssVars()` и токены в `app/styles/tokens.css`.** Токены строятся поверх `--tg-theme-*` с запасными значениями для запуска вне Telegram (по `prefers-color-scheme`). Акцент `#10b981`. Цвета вне токенов запрещены. | Решение 16 общего плана. | Хардкод цветов в компонентах. Две палитры вручную. |
| 11 | **Вне Telegram в продакшен-сборке показывается экран «Откройте из Telegram»**, вход не выполняется. В режиме разработки окружение подменяется моком SDK (`mockTelegramEnv`). | Без `initData` вход бессмысленен. Мок не должен попадать в продакшен. | Показывать рабочее приложение без Telegram. Мок за флагом в сборке. |
| 12 | **Роутер в history-режиме.** В F0 один маршрут и заглушка «Домой»; проверка, что параметры запуска во фрагменте URL не теряются, входит в ручную проверку. Если окажется, что history-режим мешает SDK, откат на другой способ записывается в раздел 9. | Решение 10 общего плана, пока не проверено на практике. | Hash-роутер сразу. |

### Режимы разработки

| # | Решение | Почему | Что отброшено |
|---|---|---|---|
| 13 | **Три режима.** (а) Моки: `VITE_ENABLE_MOCKS=true`, MSW и мок окружения Telegram, бэкенд не нужен. Сценарий выбирается параметром `?mock=` (`ok`, `new`, `banned`, `error`). (б) Против локального бэкенда: `VITE_DEV_INIT_DATA` из `scripts/dev_gen_init_data.py`, запросы идут через прокси Vite. (в) Внутри настоящего Telegram через https-туннель и тестового бота. | Этапы F0 и F1 не ждут бэкенд. Прокси Vite снимает вопрос CORS в разработке. | Только реальный бэкенд. |
| 14 | **`VITE_API_ORIGIN`: origin API без пути, по умолчанию пусто (тот же домен).** Префикс `/api/v1` входит в типизированные пути схемы. В dev Vite проксирует `/api` на адрес бэкенда из `VITE_DEV_API_TARGET`. Все `VITE_*` проверяются при запуске в одном месте и дают понятную ошибку. | Тот же код работает за прокси и за одним доменом в продакшене. | Абсолютный адрес бэкенда в коде. Проверка переменных там, где используются. Переменная `VITE_API_BASE_URL=/api/v1` (см. раздел 9, пункт 8). |
| 15 | **Правила линтера кодируют границы:** `fetch` и `XMLHttpRequest` только в `shared/api`, `@tma.js/*` и `window.Telegram` только в `shared/telegram`, `dangerouslySetInnerHTML` запрещён, импорты вверх по слоям запрещены. | Границы из `rules.md` проверяются машиной, а не ревью. | Только описание в документах. |

## 5. Тесты

Правила в `rules.md`, раздел 4: сеть подменяется MSW, запросы по роли и тексту, фикстуры строятся из сгенерированных типов.

1. `errors`: каждая из четырёх форм `detail`; враждебные входы (не JSON, `null`, число, список не-объектов, огромная строка, объект без `code`) дают `ApiError`, а не исключение.
2. `client`: добавляет `Authorization`; три параллельных запроса при `401` делают **один** вход и по одному повтору; второй `401` даёт ошибку; `403` со строкой вызывает обработчик бана; сетевой сбой и не-JSON ответ дают `ApiError`.
3. `session` и экраны: успешный вход показывает имя; `is_banned` показывает экран бана с причиной; ошибка входа показывает экран с рабочей кнопкой «Повторить»; повторный вызов входа не делает второго запроса, пока идёт первый.
4. `telegram`: вне Telegram `isInsideTelegram()` ложь, `getRawInitData()` бросает `NotInTelegramError`, методы с проверкой версии ничего не делают; внутри (мок окружения) возвращают значения.
5. `env`: отсутствующая или неверная переменная даёт понятную ошибку; флаг моков игнорируется вне режима разработки.
6. `App`: сценарии `ok`, `new`, `banned`, `error` через MSW; в «продакшен»-режиме без Telegram показывается экран «Откройте из Telegram», запросов входа нет.

## 7. Проверка (запускает человек)

```bash
cd frontend
npm ci
npm run typecheck
npm run lint
npm test
npm run build
```

Ручная проверка после части 3.

1. **Моки.** В `frontend/.env.local` задать `VITE_ENABLE_MOCKS=true`, запустить `npm run dev`, открыть в обычном браузере. Видно приветствие с именем. Адрес с `?mock=banned` показывает экран бана с причиной, `?mock=error` показывает ошибку с кнопкой «Повторить», которая работает.
2. **Реальный бэкенд.** Запустить бэкенд и сиды по корневому `CLAUDE.md`, сгенерировать `initData` через `scripts/dev_gen_init_data.py`, записать в `VITE_DEV_INIT_DATA`, убрать `VITE_ENABLE_MOCKS`, запустить `npm run dev`. Видно имя пользователя из ответа бэкенда. Данные живут 300 секунд: если вход не проходит с `401`, сгенерировать заново.
3. **Продакшен-сборка.** `npm run build && npm run preview`, открыть в обычном браузере. Показывается «Откройте из Telegram». Проверить, что мока нет в сборке: поиск `msw` по `frontend/dist` ничего не находит.
4. **Внутри Telegram.** https-туннель на `npm run preview` или dev-сервер, тестовый бот из BotFather с этим адресом, токен бота в `.env` бэкенда. Приложение открывается, показывает имя, тема совпадает со светлой и тёмной темой клиента, в адресе остались параметры запуска, кнопка «Назад» не появляется на первой странице.

Условия готовности этапа:
- все команды раздела 7 зелёные локально и в CI;
- в `dist` нет моков;
- линтер падает на `fetch` вне `shared/api` и на импорт `@tma.js/*` вне `shared/telegram` (проверить вручную, добавив нарушение и убрав);
- в корневом `CLAUDE.md` изменена только одна строка.

## 9. Отклонения

1. **Один `tsconfig.json`, без `tsconfig.node.json`.** `vite.config.ts` входит в основной проект (`include`), типы `node` подключены там же. Почему: типизированный линтер (`projectService`) должен находить проект для каждого проверяемого файла, а второй tsconfig под один файл усложняет и сборку, и линтер. Что отброшено: отдельный `tsconfig.node.json` со ссылками.
2. **Добавлен `.prettierignore`** (`dist`, `coverage`, `package-lock.json`, сгенерированная схема), чтобы `npm run format` не трогал сгенерированные файлы.
3. **Скрипт `test` временно с `--passWithNoTests`**, пока в проекте нет ни одного теста (часть 1). Флаг убран в части 2, когда появились тесты.
4. **Тесты лежат рядом с кодом** (`errors.test.ts` рядом с `errors.ts` и так далее), а не только в `tests/`. В `tests/` остаются общие настройка, обработчики MSW и фикстуры.
5. **`shared/config/tuning.ts` в F0 не создаётся.** Настраиваемых значений, которые нужны только фронтенду, пока нет; файл появится вместе с первым (например, задержка ввода подсказок тегов).
6. **Переменные `--tg-viewport-*` и `--tg-safe-area-*` в F0 не привязываются.** Для них нужно монтировать `viewport` асинхронно; это относится к безопасным зонам и откладывается на F8. В F0 `Screen` использует значения по умолчанию с запасным `0px`.
7. **`openChat(username)` возвращает `boolean`** (`false` для недопустимого имени), а не бросает ошибку: имя приходит с сервера, и экран просто не должен показывать кнопку.
8. **`VITE_API_ORIGIN` вместо `VITE_API_BASE_URL`** (решение 14). Пути в схеме из `/openapi.json` уже начинаются с `/api/v1`, поэтому базовый адрес `/api/v1` дал бы запросы на `/api/v1/api/v1/...`. Теперь в переменной только origin, пусто означает тот же домен. Что отброшено: срезать префикс из путей схемы или переписывать URL в промежуточном слое клиента.
9. **В сессии шестое состояние `not-in-telegram`** (к `idle`, `signing-in`, `signed-in`, `banned`, `error`). Вход сам обнаруживает, что `initData` нет, и ставит его; отдельная проверка среды в `App` не нужна, а вне Telegram запросов входа нет.
10. **Мок в браузере через Vite-плагин MSW 3 (`msw/vite`, модуль `virtual:msw`)**, а не через `public/mockServiceWorker.js` и `mocks/browser.ts`. Файл в `public/` попал бы в `dist/` и нарушил бы условие «в сборке нет `msw`»; плагин отдаёт worker только в dev. Вместо `browser.ts` теперь `mocks/index.ts`.
11. **В моках `profiles` пустой во всех сценариях.** F0 анкеты не показывает; сценарии различаются бан, новый пользователь и ошибка. Сценарий `error` падает один раз, чтобы «Повторить» было видно в работе.
12. **Привязка «Назад» к роутеру в F0 не делается.** Маршрут один, кнопка по умолчанию скрыта. Привязка появится вместе со вторым маршрутом (F2), иначе это нетестируемый код без пользы. Обёртка `backButton` и её монтирование уже есть.
13. **`resetSession()` экспортируется для тестов.** Хранилище сессии живёт в модуле, без сброса тесты влияли бы друг на друга.
14. **В `vite.config.ts` добавлен `preview.allowedHosts: ['.trycloudflare.com']`.** Сервер превью отклоняет неизвестные хосты, а https-туннель для проверки в настоящем Telegram отдаёт приложение под меняющимся доменом `trycloudflare.com`. Проверка в Telegram идёт через `npm run build && npm run preview`, а не через `dev`: в dev значение `VITE_DEV_INIT_DATA` перекрыло бы настоящие данные Telegram.
